# Dorker Agent Lab

A safe development workspace inside the Dorker Skills repository.

## Components
- `dorker_agent/`: provider-agnostic agent scaffold, validated task envelope, default-deny capability policy, optional framework adapters, and a PostgreSQL audit repository adapter.
- `tests/`: unit tests for agent, task validation, capability policy, and framework adapters.
- `.github/ISSUE_TEMPLATE/`: structured bug and feature intake.
- `.github/pull_request_template.md`: change, verification and rollback checklist.
- `.github/workflows/agent-lab-ci.yml`: GitHub Actions CI.

## Remote audit persistence

`PostgresAuditRepository` implements the remote audit repository contract against the private `remote_audit` schema using psycopg 3. It uses transaction-scoped advisory locks for per-repository sequence allocation, verifies the hash chain and head before reads/writes, and commits the event, head, plan/decision, and evidence-consumption rows atomically. Configure it with a server-side DSN via `PostgresAuditRepository.from_dsn(...)`; never use the Supabase owner credential in an application or GitHub Actions runtime. The CI workflow starts an ephemeral PostgreSQL 16 service, applies the schema, and runs integration tests for idempotency and concurrent first appends. These tests do not connect to the user's Supabase project. `agent-lab/postgres/002_remote_audit_app_role.sql` provisions a NOLOGIN/NOBYPASSRLS group role with SELECT/INSERT grants and UPDATE only on `heads`; RLS policies are scoped to that role. The policy permits all repository IDs because this is a trusted single-service account, not tenant isolation. CI creates an ephemeral `remote_audit_login` LOGIN role and connects to PostgreSQL directly with that role (not `SET ROLE` from the admin connection). Integration tests assert that the login inherits only the intended app-role grants, has no superuser or `BYPASSRLS` privilege, and does not own the audit tables. The CI password is disposable and exists only in the ephemeral PostgreSQL service. For deployment, create a separate LOGIN role with a password generated outside GitHub, grant it membership in `remote_audit_app`, and store its DSN only in the server secret manager. Keep table ownership with a separate migration/admin role; PostgreSQL table owners can bypass RLS unless `FORCE ROW LEVEL SECURITY` is enabled. Never grant BYPASSRLS or use the owner/service-role credential. External integrity checkpoints and lost-response-after-commit fault injection remain separate work.

## Artifact storage
Create the artifact root directory with restrictive OS permissions before constructing `ContentAddressedArtifactStore`. Configure `max_artifact_bytes` to bound each object. The POSIX store publishes immutable blobs under SHA-256 paths and verifies bytes on read. `SQLiteArtifactIndex(database, blob_store)` adds durable manifest metadata: `put(bytes, ...)` stores the blob then indexes a deterministic artifact ID; `get(artifact_id)` returns the manifest and checksum-verified bytes; `list_for_execution(execution_id)` finds artifacts associated with an execution. Repeated registration of the same manifest is idempotent, while identical bytes can have separate manifests for different execution IDs. The index has a bounded record count and SQLite WAL/busy-timeout handling. Blob publication occurs before the index transaction, so an index failure can leave an unindexed blob; it will not create a manifest pointing to a blob that was not published. The execution ID is a logical association, not a foreign key to `SQLiteExecutionStore`. Both stores are single-host components. There is no global disk quota, deletion-capable garbage collector, encryption, or automatic orphan cleanup. `SQLiteArtifactIndex.dry_run_gc(max_scan_objects=...)` performs a bounded, read-only scan and reports verified unreferenced blobs, missing indexed blobs, corrupt blobs, and whether the scan was truncated. It never deletes or mutates objects; malformed paths and non-regular entries are ignored. Review the report and back up both stores before any separately designed deletion workflow. `build_gc_plan(ArtifactRetentionPolicy(...))` creates a non-destructive candidate plan using filesystem modification time, a minimum age, a bounded candidate count, and a bounded full scan. It refuses truncated scans. The plan includes candidate digests, sizes, cutoff, and a deterministic SHA-256 approval token. This token is an integrity fingerprint of the proposed plan, not an authenticated approval; no deletion API exists. Any future deletion implementation must re-scan and compare the approved token immediately before deletion, then require explicit operator approval. `record_gc_plan(plan, claim=...)` and `record_gc_approval(token, claim=..., approved=...)` persist plan creation and approval/rejection events in a bounded SQLite audit table. `GitHubActorClaim` carries a GitHub numeric user ID, login, and short-lived OIDC token; a trusted, injected `GitHubIdentityVerifier` must validate the token and return the canonical `VerifiedGitHubActor`. Audit calls fail closed if no verifier is configured. Approval is rejected when the approver's immutable GitHub ID matches the plan creator; a plan token can be recorded once and can receive only one approval/rejection decision. The token is never persisted. Events form a SHA-256 hash chain; `verify_audit_log()` detects accidental or unsophisticated database edits. `GitHubActionsOIDCVerifier` now validates RS256 JWT signatures with the vetted `cryptography` package (declared in `agent-lab/requirements.txt`) against the fixed GitHub Actions JWKS endpoint, bounds JWKS/token sizes, rejects duplicate JSON keys and weak RSA parameters, and enforces issuer, audience, expiry/issued-at/not-before, repository and immutable repository ID, exact workflow-ref allowlist, optional exact subject allowlist, and signed actor ID/login. Configure `GitHubOIDCPolicy` with the numeric repository ID and exact workflow ref(s); do not use wildcard workflow refs. `GitHubActionsJWKSProvider` uses HTTPS with bounded response size and timeout. `GitHubActionsOIDCTokenProvider` obtains a short-lived JWT from the runner-provided `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN`, requests the configured audience, pins the HTTPS endpoint host to `pipelines.actions.githubusercontent.com`, rejects redirects, bounds request/response sizes and timeouts, and never logs or persists either credential. `GitHubActionsOIDCIdentityProvider(token_provider, verifier)` composes acquisition and verification: `acquire_claim()` obtains the runner token and extracts actor fields from its untrusted payload only to construct a claim; `SQLiteArtifactIndex` then calls the provider's `verify()` method, which validates the signature and all configured signed claims before accepting the actor. The extracted fields are never trusted until verification succeeds. Alternatively, callers may construct claims explicitly and inject `GitHubActionsOIDCVerifier` directly. Construct this provider only in a trusted host/controller process, never inside an untrusted worker or container. The repository's normal CI deliberately has no `id-token: write` permission and does not request OIDC tokens. Production deployment must separately review the host adapter, OIDC permission scope, environment protection, workflow/ref policy, and key-rotation/availability behavior. Never trust `GITHUB_ACTOR` environment variables or login text alone. The hash chain is not tamper-proof against an administrator who can rewrite the database and recompute hashes; signed external checkpoints are not implemented. Audit capacity is bounded by `max_audit_records` and fails closed when full.

## Agent contract
The base agent accepts a task and an injected model adapter. It exposes no shell, filesystem, network, deployment, or secret access. Tool execution is not implemented.

## Framework adapters
- `CrewAIAdapter` accepts an injected object exposing `kickoff(inputs=...)`.
- `LangChainAdapter` accepts an injected Runnable exposing `invoke(input)`.
- Both adapters are synchronous, accept only `TaskRequest`, normalize plain-string responses or framework text fields (CrewAI `raw` / LangChain `content`), and wrap framework exceptions.
- Each adapter requires its own explicit capability: `framework:crewai` or `framework:langchain`. The default policy denies both.
- `InMemoryExecutionLedger` is process-local. `SQLiteExecutionStore` persists lifecycle state across restarts, uses SQLite transactions/WAL, enforces a record and result-size limit, and rejects duplicate execution IDs across store instances. Both implement the adapter ledger interface.
- Framework packages are not imported or installed by Agent Lab. The caller is responsible for constructing and configuring the injected object.
- Framework-native tools are not granted by these adapters. Do not pass a preconfigured crew/runnable with tools or external side effects unless separately reviewed and explicitly authorized.

## Execution boundaries
Execution control is cooperative: pass an `ExecutionControl` to an adapter and provide a context-aware port (`kickoff_with_context` or `invoke_with_context`) that polls `control.check()`. The control exposes thread-safe `cancel()`, `cancelled`, `remaining_seconds()`, and a monotonic deadline. A cancellation/deadline error is recorded as a failed execution. For hard wall-clock termination, `IsolatedWorkerRunner` starts a fresh `spawn` process, accepts only explicitly registered importable handlers, JSON-safe bounded payloads/results, and performs cooperative cancel → terminate → kill → join cleanup. On POSIX, the worker creates a new session/process group; the parent signals the group on exit so ordinary subprocess descendants are stopped. `ResourceLimits` can optionally apply POSIX `RLIMIT_CPU`, `RLIMIT_AS`, `RLIMIT_NOFILE`, and `RLIMIT_FSIZE` before handler execution. The parent owns optional ledger transitions; child processes never write the ledger. These controls are not a security sandbox: a handler can deliberately escape its process group (for example, by creating a new session), rlimits are platform-dependent and do not constrain every kernel resource, and filesystem/network/syscall access is not isolated. Windows supports worker termination but not these POSIX controls. Handlers are trusted code and must be top-level/importable for `spawn`; arbitrary dynamic imports and shell execution are not provided. The runner does not automatically wrap CrewAI/LangChain objects; framework integration needs an explicit serializable handler contract. The adapters do not implement asynchronous task cancellation, retries, distributed idempotency, sandboxing, or framework tool isolation. The SQLite store is single-host durability, not distributed exactly-once execution. Call `recover_interrupted()` once during controlled startup before accepting work; it marks all leftover `running` records as `failed/ProcessInterrupted` and never automatically replays them. Do not run this recovery concurrently with active workers. Results are persisted (up to the configured limit), so protect the database and WAL files with OS permissions and encrypted storage when outputs may contain sensitive data. There is no retention/compaction policy yet. Do not treat capability checks as a security boundary against arbitrary code inside an injected framework object. Keep framework objects trusted and runtime disabled until an isolated execution contract is implemented and tested.

## Status
- Implemented: synchronous injected ports, explicit capability gates, task mapping, response validation, exception wrapping, and fake-port unit tests.
- Implemented: process-local ledger plus durable SQLite store, transactional single-use execution IDs, bounded record/result sizes, interrupted-run marking, deterministic connection closing, and adapter integration.
- Implemented: multiprocessing tests for same-ID contention, concurrent distinct jobs, and abrupt worker termination followed by controlled recovery.
- Implemented: cooperative cancellation and monotonic deadline checks for context-aware injected ports; blocking calls are not forcibly interrupted.
- Implemented: `ContainerSandboxConfig`, host bind mounts disabled by default with explicit `allow_host_mounts=True` opt-in plus mount allowlisting, immutable repository-digest or local content-addressed image-ID validation, non-root identity, bounded resource policy fields, and `ContainerSandboxRunner`.
- Implemented: deterministic `ArtifactManifest` metadata and byte verification for bounded artifacts; manifest fields are not signed or authenticated.
- Implemented: `GitHubActionsOIDCIdentityProvider` composes the runner token provider with the signed-claim verifier and implements the artifact index identity-verifier interface. It extracts actor fields only as untrusted claim inputs; the verifier checks signature, repository/workflow policy, and actor equality before the index accepts the identity. Unit tests use a synthetic RSA token and fake token source; no live runner token was requested.
- Implemented: bounded SQLite artifact GC audit log, SHA-256 hash chain, one-time plan registration, single decision per plan, and a distinct-immutable-GitHub-ID approval gate behind an injected `GitHubIdentityVerifier` contract. Audit writes fail closed when no verifier is configured. A concrete OIDC/JWKS verifier and trusted runtime integration are not implemented; tests use a fake verifier. The chain has no external signed checkpoint.
- Implemented: bounded, read-only `SQLiteArtifactIndex.dry_run_gc()` scans canonical SHA-256 objects and reports unreferenced, missing, and corrupt objects; it never deletes files and marks truncated scans.
- Implemented: `SQLiteArtifactIndex` persists deterministic manifest IDs and metadata, supports execution-ID lookup, bounded record count, idempotent registration, and verifies the blob plus manifest before returning data. Blob publication precedes index commit; failed index writes may leave unindexed blobs. Execution ID is a logical reference, not an enforced foreign key to the execution ledger.
- Implemented: `ContentAddressedArtifactStore` stores immutable bytes under SHA-256 shard paths, publishes with same-filesystem atomic hard links, uses no-follow directory/file opens, mode `0600` objects, verifies digest on read, rejects symlink roots/shards/objects, and enforces a per-artifact byte limit. The root must be pre-created and trusted. This is POSIX-only, single-process thread synchronization plus atomic cross-process publication; it does not provide a global disk quota, retention/GC, encrypted storage, or authenticated manifest persistence.
- Implemented: SHA-256 integrity metadata for bounded stdin/stdout/stderr streams, with constant-time expected-stdout digest verification and optional runner-enforced `expected_stdout_sha256`; mismatch fails the execution ledger before success. This is not a signed attestation.
- Implemented: `DockerCLIContainerRuntime` invokes Docker CLI with argv (never shell), `--pull=never`, network disabled, read-only rootfs, all capabilities dropped, no-new-privileges, non-root UID/GID, memory/CPU/PID limits, bounded tmpfs, explicit bind mounts, and bounded concurrent output capture. Bounded artifact input is streamed through container stdin (`input_payload` / `max_input_bytes`), avoiding host bind mounts for ordinary task inputs. `ContainerSandboxConfig.input_sha256` exposes the input payload digest; `ContainerResult.stdout_sha256` and `stderr_sha256` expose SHA-256 digests of the exact bounded output streams, and `verify_stdout_sha256()` verifies an expected stdout digest using constant-time comparison. Set `expected_stdout_sha256` on the config to make the runner reject a mismatched stdout stream and mark the ledger entry failed before reporting success. The combined stdout/stderr byte limit remains enforced by the Docker runtime and runner. `ArtifactManifest` records a plain filename, media type, byte size, SHA-256, source label, optional execution ID, and optional caller-supplied timestamp. `from_bytes()` computes size and digest; `verify()` enforces a caller-provided maximum size and compares content; `to_json()` emits deterministic canonical JSON. Manifest metadata is not a signed provenance claim: `source`, execution ID, and timestamp are caller-supplied and require a trusted signer/ledger to authenticate. `ContentAddressedArtifactStore` can persist raw bytes separately by digest; manifests remain caller-owned metadata and are not automatically persisted alongside objects. These digests provide integrity metadata, not a signed attestation. Timeout/cancellation/output overflow attempt to stop the container by its cidfile before terminating the CLI. Mount paths are canonicalized, checked against allowlisted roots, and Unix sockets are rejected. Host bind mounts remain a TOCTOU-sensitive operation because Docker resolves source paths in the daemon; use only trusted, non-mutating host directories and never expose writable mounts to untrusted tasks. The explicit opt-in prevents accidental host-data exposure but does not eliminate races.
- Security boundary: Docker daemon, CLI binary, host kernel, and daemon access remain trusted. Never mount the Docker socket or pass daemon credentials to agents. Docker's default seccomp profile is relied upon; no custom profile is bundled. This is not a defense against kernel/container-runtime vulnerabilities.
- Not implemented: bounded artifact output extraction to a structured file format (stdout/stderr remain the output channels), signed provenance/attestation, Podman adapter, custom seccomp profile management, Windows Job Objects, automatic retry/replay, distributed idempotency, multi-host coordination, retention/compaction, deletion-capable garbage collection, or proof of hostile-code containment.
- Validation: GitHub Actions runs real Docker daemon integration tests for non-root UID/GID, dropped effective capabilities, no-new-privileges, read-only rootfs, writable bounded `/tmp`, absence of a default network route, cgroup memory/CPU/PID limits when exposed by the host, read-only host bind mounts, Docker-socket absence, timeout termination, and output-limit termination. Adversarial unit tests cover symlink escape after path resolution, mount-root prefix confusion, and Docker-option injection through command arguments. These tests validate the tested runner/daemon combination only; they do not establish hostile-code containment or cross-host portability.
